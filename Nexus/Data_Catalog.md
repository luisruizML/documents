# **Data Catalog at Nexus**

*Companion document to* `Data_Principles.md` *P6 (Ready for AI) and Q2 (Quality is a precondition, not a clean-up), and to* `Lakehouse_Architecture.md` *(Honest Trade-Offs: "A catalog is now a dependency"). This document expands on why a Lakehouse specifically — not a database in general — requires a catalog service to remain discoverable, and argues why OpenMetadata is Nexus's concrete answer.*

**Part:** 3 — How it is built · **Document:** 21 of 22 · **Version:** 0.1 · **Status:** Draft · **Last Updated:** 2026-09-22

## **Executive Summary**

`Lakehouse_Architecture.md` already names the catalog as an operational dependency: Iceberg and Delta Lake both need one to resolve table names to metadata, and that catalog's availability becomes load-bearing for every query — one more component Nexus has to run reliably. That argument is correct as far as it goes, but it's an argument about *uptime* — what breaks if the catalog goes down. It says nothing about a more basic problem that exists even while the catalog is perfectly healthy: without it, there is no single place where "what data exists in Nexus, and who owns it" can even be asked as a question, let alone answered. A Lakehouse table nothing indexes doesn't stop existing — it just stops being findable, the same way a book pulled from a library's card catalog doesn't vanish from whatever shelf it's still sitting on.

This document argues that a Lakehouse specifically — as distinct from "a database" in the generic sense — creates this problem by design, because it deliberately gives up the one thing a single database engine provides for free: a built-in, engine-enforced namespace that makes every table it holds inherently listable. Nexus's answer is OpenMetadata — the "Data Vigilante" — and it is not a bolt-on nice-to-have layered on after the fact — Annex C.3 makes catalog registration a gate on Dominion creation itself, and Annex C.6's Certification Gate is enforced inside it. The catalog is the specific mechanism that turns "a pile of tables that happen to work" into a data platform other Dominions, and the AI agents Data Principles P6 prepares for, can actually find, understand, and trust.

## **Why a Lakehouse Specifically Needs a Catalog**

A single database engine gives you a namespace whether you asked for it or not. You cannot create two tables named `citizens` inside one PostgreSQL instance — the engine itself refuses the second `CREATE TABLE`. And `information_schema` always knows, and will always tell you, exactly what tables exist, what columns they have, and what types those columns are. Discoverability, at this generic-database scale, is not a feature anyone had to build — it's a side effect of there being exactly one thing in charge of the namespace.

Nexus deliberately does not build that way, and commits to the alternative on purpose (Data Principles L2, P6):

* **Many independent tables, not one engine.** Every Dominion owns its own Bronze/Silver/Gold Iceberg/Delta tables. There is no single database process that all of them run inside — they are files in object storage, written and read by whichever compute engine (Spark, Flink, dbt, FastAPI) happens to be attached to that layer at that moment. Nothing plays the role PostgreSQL plays for a single database: nothing refuses a name collision, because nothing is watching all the names at once.
* **A table's identity is scattered, not centralized.** An Iceberg or Delta table's schema, snapshot history, and partitioning live in metadata files sitting alongside the data files that make it up — see `Lakehouse_Architecture.md`'s account of how time-travel works directly out of this file layout. That metadata is real and complete, but it only describes *that one table*. Nothing rolls it up into a queryable "what exists" view across Dominions and layers unless something is built specifically to do that rolling-up.
* **This is a deliberate trade, not an oversight.** Nexus chose the Lakehouse specifically to get decentralized Dominion ownership, independent per-layer scaling, and cheap object storage (all argued for in `Lakehouse_Architecture.md` and its Medallion-layering counterpart). Giving up the single-engine namespace is the price of that choice, not a bug to be patched — but it is a real, structural gap that has to be filled by something, or three things quietly break:
  * **Name collisions go unnoticed.** Two Dominions, working independently, can each stand up a table that answers to the same implicit concept — "citizen mobility," say — under different names, with nobody positioned to notice, because no engine is refusing the second one the way PostgreSQL would.
  * **"What data products exist, and who owns them" has no answer.** Not a slow answer, not a manual one — no answer at all, because there is no registry to query. Asking it means asking people, and people leave, forget, or were never told.
  * **Annex C.6's Certification Gate has nowhere to live.** The gate requires a data product to carry a verified "certified" status before another Dominion may consume it. A status has to be *stored* somewhere and *checked* by something — without a catalog, there is no registry for that status to exist in, and the gate collapses from an enforcement mechanism back into a policy nobody can actually verify.

Discoverability isn't a nice-to-have layered on top of a Lakehouse after the fact — it's the thing that turns "a pile of tables that happen to work" into a data platform other Dominions, and AI agents, can actually find and trust. A generic single database gets this for free. A Lakehouse, organized as a Data Mesh the way Nexus specifically chose, has to build it.

## **What "Discoverable" Actually Means**

"Discoverable" is doing a lot of work in that sentence, so it's worth being concrete about what it breaks down into. A catalog earns the name only if it delivers all four:

* **Findability** — can a human, or an AI agent, search for "what data exists about citizen addresses" and get an answer without already knowing which Dominion or which table to look in first? Without a catalog, finding a dataset means knowing someone who already knows it exists — tribal knowledge that doesn't scale past the person who happens to remember. With one, it's a search query against a single index that spans every Dominion and every Medallion layer.
* **Self-description** — does a table carry its own schema, description, and owner, or does understanding it require out-of-band documentation — a wiki page, a spreadsheet, a Slack thread — that inevitably drifts out of sync with the table it was supposed to describe? Documentation that lives apart from the asset it describes rots the moment the asset changes and nobody remembers to update the other place. Documentation that lives *in* the catalog, attached to the asset, is the thing a schema-change review actually touches.
* **Lineage** — can you trace a Gold table's numbers back through the Silver transformation and the Bronze source that produced them? This is the direct extension of the traceability argument `Lakehouse_Architecture.md` already makes for time travel: time travel tells you what a table looked like at a past snapshot; lineage tells you *how* that snapshot came to contain what it does — which upstream tables, and which transformation, produced it. Time travel without lineage answers "what changed"; lineage without time travel answers "where did this come from." A catalog is where both questions get answered from the same place.
* **Trust signaling** — does the catalog surface whether a data product is certified, so a consumer — human or AI agent — knows whether it's safe to build on before they build on it? A table that exists, is findable, and is self-described is still not the same as a table someone with real accountability has vouched for. Trust signaling is what separates "I found a table that looks right" from "I found the table this Dominion has certified is right," which is exactly the distinction Annex C.6 exists to enforce.

## **Nexus's Answer: OpenMetadata as the Data Vigilante**

OpenMetadata is the semantic and governance backbone: it gives AI agents the context they need to operate safely and accurately, ensuring every asset is continuously documented, labeled, tagged, and lineage-tracked. Two mechanisms already committed elsewhere in this documentation set are what make that concrete rather than aspirational:

* **Annex C.3 — registration is a creation-time gate, not optional paperwork.** A Dominion cannot publish to Silver or Gold at all without, at minimum, "OpenMetadata registration: schema, owner, SLA." This is deliberately positioned *before* publication, not after — a table cannot go live undiscoverable and get cataloged later as a cleanup task, because there is no "later": the gate blocks the publish itself. This is what prevents the data-swamp risk the Technical Foundations risk register names, and it's the same mechanism that keeps the name-collision and ownerless-table problems described above from ever occurring in practice — a Dominion literally cannot skip registering the name.
* **Annex C.6 — the Certification Gate is enforced *inside* OpenMetadata.** "Certified" isn't a status tracked in a spreadsheet next to the catalog; it's a status the catalog itself carries, verified by an automated policy check or a designated reviewer, and checked before any consuming Dominion is allowed to build on the product. The trust-signaling piece of discoverability above isn't a separate system — it's a field on the same asset record that carries the schema and the owner.

This also gives Data Principles P6 (Ready for AI) an actual mechanism rather than a hope. That section argues that advanced AI and autonomous agents "cannot function on fragmented data" — but an agent given free rein over the Lakehouse has a sharper problem than fragmentation: it cannot safely query data it doesn't know exists, and it cannot trust data whose lineage and ownership it has no way to verify. An agent with catalog access can ask "what certified data products exist for citizen mobility, who owns them, and what feeds them" as a structured query and get a structured answer — the exact context Data Principles P6 promises it. Without the catalog, an agent either can't ask the question at all, or has to be handed the answer by a human every time — which is not autonomy, it's a human turned into an API. This is the same pattern the rest of this documentation set keeps returning to: a one-line Data Principles commitment becomes a real mechanism only once its companion document names exactly what enforces it.

## **Worked Example: Finding "Citizen Mobility" Before Building It Twice**

A new Data Scientist joins the Transportation Dominion. Their first assignment is a citizen-mobility analysis — trip patterns, mode share, commute distances — for an upcoming infrastructure proposal. Before writing a single query against a source system, they need to know one thing: does a "citizen mobility" dataset already exist anywhere in Nexus, built by some other Dominion, that they should build on instead of duplicating?

**With the catalog.** They open OpenMetadata and search "citizen mobility." Within minutes, the search surfaces a certified Gold table — `mobility.citizen_trip_summary` — owned by the Registry Dominion, built eight months earlier for a different project. The asset record shows its schema, its accountable owner, its SLA tier, and its certification status at a glance. One more click follows its lineage back through the Silver transformation that resolved trip events against `Subject 360` identities, and further back to the Bronze sources — transit-card swipes and vehicle-registration events — that fed it. The Data Scientist now knows, before writing any code, exactly what exists, whether it's safe to build on, and who to ask if they have a question the catalog doesn't answer. The work that follows is an extension of a certified asset, not a new one built in the dark.

**Without the catalog.** The same Data Scientist asks around. Nobody on their immediate team has heard of a mobility dataset. They post in a Dominion Slack channel and get a "maybe check with Registry?" three days later. Registry's channel takes another week to respond, and the answer — from someone who happens to remember — is a guess at a table name, no schema, no documentation, no certification, and no confidence it's still the current version. Rather than wait longer, the Data Scientist builds their own version from source. Three months later, in an unrelated planning meeting, it comes out that the Registry Dominion built almost exactly this dataset the year before. By then, two uncertified, undocumented, mutually unaware copies of the same conceptual dataset exist in Nexus — and because neither one was ever registered, a *third* Dominion evaluating the same question next quarter will have exactly as hard a time finding either of them as this Data Scientist did finding the first.

The difference isn't speed alone — it's whether "does this already exist" is a question the platform can answer at all, or one that depends entirely on who happens to still be reachable and still remembers.

## **Strengths**

| Strength | What it actually buys Nexus |
| --- | --- |
| Prevents duplicate, uncertified data products | The worked example above is the failure mode this directly prevents — a Dominion searches before it builds, instead of discovering a duplicate exists three months and one wasted project later. |
| Makes the Certification Gate actually enforceable | Annex C.6's "certified" status is a field OpenMetadata tracks and checks, not a claim in a document nobody consults — the gate has real teeth because the registry it depends on exists. |
| Gives AI agents a place to verify trust before consuming data | Data Principles P6 (Ready for AI) stops being aspirational: an agent can query certification, owner, and schema before acting, instead of needing a human to vouch for a dataset every time. |
| Turns lineage from "ask around" into a queryable fact | Tracing a Gold table's numbers back to their Silver and Bronze origins (the traceability argument `Lakehouse_Architecture.md` makes for time travel) becomes a lookup in the catalog, not a request to whoever built the pipeline and might still work here. |
| One index across every Dominion and layer | A search spans Bronze, Silver, and Gold, and every Dominion, from a single entry point — nobody has to already know where to look before they can look. |

## **Honest Trade-Offs**

| Trade-off | The real cost |
| --- | --- |
| The catalog is a load-bearing single point of failure | `Lakehouse_Architecture.md` already names this for query execution — a catalog outage blocks every table-name resolution. This document's argument makes the same dependency worse in a second way: even while the catalog is technically up, if it is slow, ungoverned, or partially adopted, discoverability itself degrades right along with it — the platform doesn't just fail to run queries, it fails to be knowable. |
| Catalog metadata needs its own ongoing governance discipline | A stale or wrong description, owner, or certification status in OpenMetadata is arguably worse than having no catalog at all — a missing entry prompts someone to ask around, but a wrong entry actively misleads a human or an agent into trusting the wrong thing. The catalog is only as trustworthy as the discipline that keeps it current, and that discipline is never free. |
| Registration is real, ongoing operational overhead | Annex C.3's minimum registration at Dominion creation is only the starting cost. Every subsequent schema change, every new asset, every ownership handoff has to be reflected in OpenMetadata too — this is recurring work every Dominion carries for the life of every data product it owns, not a one-time setup step it completes and moves past. |

## **Verdict**

`Lakehouse_Architecture.md` was right to flag the catalog as a dependency — but availability is only half of what makes it load-bearing. The other half is that a Lakehouse, by the deliberate design choices Nexus commits to (Data Principles L2), gives up the one thing a single database engine hands you for free: a namespace that makes every table inherently listable. Nothing else in the architecture fills that gap. OpenMetadata — the "Data Vigilante" — is what fills it, and it does so through mechanisms already committed elsewhere in this documentation set rather than through a bolt-on tool: Annex C.3 makes registration a gate a Dominion cannot publish around, and Annex C.6's Certification Gate is a status the catalog itself enforces. Discoverability was never a feature to add once the Lakehouse was working — it's the specific mechanism that makes Data Principles P6 (Ready for AI) achievable rather than aspirational, and the reason a Lakehouse without a catalog is not a smaller version of a data platform, but not one at all.
